### Harness Sync Prompt (copy into an AI session opened in your evolving project)

Reverse-distill the latest universal guardrails from this project (SOURCE, the current repository) into the starter toolkit `harness_agent_project_bootup` (TOOLKIT). If you do not know the TOOLKIT path, ask before starting.

Do not rely on a fixed file list. Derive every scope from the code, so this prompt keeps working when the harness architecture changes.

---

### 0. Self-check (stop on failure)

- Confirm that TOOLKIT contains `bootstrap_harness.py`, and that this script defines the generated-file map (currently the `FILES` dict, plus any `FILES["..."] = ...` assignments).
- Confirm that the generated verification entrypoint still exists in that map (currently `tools/verify.py`).
- If either assumption no longer holds, stop. Report which step of this prompt is stale and what replaced it. Do not guess.

### 1. Inventory from TOOLKIT (source of truth for scope)

- Parse `bootstrap_harness.py` and list every path that it generates.
- Read the limits and rules from the generated checkers themselves (for example `LIMITS`, `STATE_LIMIT`, `MAX_LOG`, planning checks in `tools/check_docs.py`). Do not copy numbers from this prompt or from README.

### 2. Compare SOURCE against the inventory (read-only)

For each generated path, compare the TOOLKIT template with the SOURCE file and classify it:
- **Universal improvement**: a new or stricter rule, check, hook or test that applies to any project. Candidate to sync.
- **Domain-specific**: entity names, business or game mechanics, proprietary libraries. Do not sync; generalize it only if an abstract version is useful.
- **Weaker in SOURCE**: the TOOLKIT version is stricter. Keep TOOLKIT; never downgrade a guard.
- **Unchanged or missing in SOURCE**.

Do not modify any file in SOURCE.

### 3. Discover governance that TOOLKIT does not cover yet

Search SOURCE for governance files that are not in the inventory:
- files referenced from `AGENTS.md`, `ARCHITECTURE.md`, git hooks, agent settings, or the verification pipeline;
- everything under the hook directory, agent configuration directories, `tools/`, and documentation-policy docs;
- CI workflows that run checks.

List each candidate with its purpose and a recommendation (add, generalize, or skip). Add only universal ones.

### 4. Rule-to-enforcement traceability

For every rule in the SOURCE and TOOLKIT `AGENTS.md` / `ARCHITECTURE.md` that claims mechanical enforcement:
- name the checker function that enforces it;
- name the regression test that proves the checker rejects a violation.

Every synced rule needs both. Report rules that are text-only, or that are enforced but not tested.

### 5. Apply to TOOLKIT

- Update the templates in `bootstrap_harness.py`. Keep generated tools standard-library Python 3, cross-platform console encoding safe (CP950 / UTF-8), with LF line endings.
- Keep `AGENTS.md` the single source of truth, and keep the thin entrypoints for other agents that the inventory contains.
- Keep every generated document within the budgets that the checkers enforce.
- Update `README.md`: describe new mechanisms, and make the directory blueprint match the inventory exactly.
- If the generated-file map or the verification entrypoint was renamed, update step 0 of this prompt.

### 6. Verify in a sandbox (mandatory)

In a new temporary directory outside both repositories:
1. Run `git init`, then `python <TOOLKIT>/bootstrap_harness.py TestProject`. It must exit 0 (bootstrap returns non-zero when initial verification fails).
2. Run the verification entrypoint and every generated test file. All must exit 0.
3. For each rule synced in this run, create a violation and show that the relevant checker exits non-zero. Then revert the violation.
4. Delete the temporary directory.

### 7. Report, then commit

Report:
- the inventory classification from step 2 (path, status, action);
- the new candidates from step 3;
- traceability gaps from step 4;
- verification evidence from step 6 (commands and exit codes).

Then, in TOOLKIT, stage only the files that you changed (no `git add .`), and commit with a semantic message. Push only after the user approves the report.
